# POS System Changes — 2026-07-29

## Overview
This document captures all changes made to the pharmacy POS system on **2026-07-29**. The work focused on three areas:
1. Simplifying the customer credit / checkout payment flow
2. Removing the credit limit feature
3. Fixing runtime issues (blank screen + McKesson auto-import SQLite parameter limit)
4. Restoring the full checkout UI with product search, selectable items, receipt, past sales, hold/park, and card payment
5. Fixing catalogue upload to properly add all products and renaming "inventory" to "catalogue"
6. Fixing barcode unique constraint error during catalogue commit

- It exposed a separate "Pharmacy Credit tender" input that confused cashiers
- It had a dedicated `TAB` tender type alongside `CASH`, `CARD`, and `SPLIT`
- Overpayment handling was buried in JSX rather than presented as clear options
- Underpayment had no clear path unless the cashier manually entered a tab amount

### Solution

#### a) Removed `TAB` as a separate tender type
**File:** `src/shared/types.ts`
- `CreateTransactionPayload.tenderType` changed from `'CASH' | 'CARD' | 'SPLIT' | 'TAB'` to `'CASH' | 'CARD' | 'SPLIT'`
- `tabAmountCents` remains on the payload, but is now just an amount field rather than a tender mode
- `cashOverageToCreditCents` remains for depositing cash overpayment to customer credit

#### b) Simplified CheckoutScreen payment section
**File:** `src/renderer/src/screens/CheckoutScreen.tsx`

**Before:**
- "Tender" card with:
  - "Cash tendered" input
  - Separate "Pharmacy Credit tender" input (showed current balance, allowed manual entry)
  - "Complete Cash Sale" and "Charge Card" buttons
  - Hidden logic for `tabDollars` state

**After:**
- "Payment" card with:
  - Single "Cash received" input
  - **Overpaid path:** Shows "Give change ($X)" and "Deposit $X to credit" buttons
    - Deposit option requires a customer to be attached; otherwise shows disabled state with tooltip
  - **Underpaid path:** If customer attached, shows "Put $X on [Customer]'s tab" button
    - If no customer attached, shows warning: "Not enough cash. Attach a customer to put the remaining $X on their tab."
  - Bottom action buttons: "Pay Cash" and "Pay Card"

**Behavior changes:**
- Removed `tabDollars` state entirely; tab amount is derived from `shortCents` automatically
- `completeSale()` signature changed from `(tenderType: string, _customerId?, depositCents?)` to `(tenderType: 'CASH' | 'CARD' | 'SPLIT', tabAmountCents?, cashOverageToCreditCents?)`
- Customer attachment card now shows live credit balance (`Credit: $X` or `Owes: $X`)

## 4. McKesson Auto-Import SQLite Parameter Limit Fix

### Problem
When running `catalog:autoImport` with a large WEBCAT file, the import crashed with:
```
Query parameter limit exceeded error: Parameter limits for this database provider
require this query to be split into multiple queries, but the negation filters
used prevent the query from being split.
```

### Root Cause
In `autoImportCatalog()` at line 805 of `src/main/catalog/importService.ts`, the code was querying for "new" products using:
```ts
db.product.findMany({
  where: {
    origin: 'CATALOG',
    lastSeenBatchId: batch.id,
    sourceItemNumber: { notIn: [...previousItemNumbers] }
  }
})
```
When `previousItemNumbers` contained 65,000+ item numbers from the previous catalogue, SQLite's parameter limit (~999) was exceeded because each `notIn` value becomes a bound parameter.

### Solution
**File:** `src/main/catalog/importService.ts`

Changed the "new items" detection from a database-side `notIn` filter to an in-memory filter:

1. Query all products for the current batch without the `notIn` clause:
```ts
const batchProducts = await db.product.findMany({
  where: {
    origin: 'CATALOG',
    lastSeenBatchId: batch.id
  },
  select: { ... },
  orderBy: { name: 'asc' }
})
```

2. Filter in JavaScript using a `Set`:
```ts
const newProducts = batchProducts.filter(
  (p) => p.sourceItemNumber != null && !previousItemNumbers.has(p.sourceItemNumber)
)
```

This avoids the SQLite parameter limit entirely because the large set membership test happens in memory, not in the SQL query.

## 6. Catalogue Upload Fix — Add All Products

### Problem
When uploading a McKesson WEBCAT file with thousands of products, only about 30 products were being added to the catalogue. The rest were silently skipped.

### Root Cause
**File:** `src/main/catalog/catalogQueries.ts`

The `promoteAllCatalogProducts()` function was using `createMany` with `skipDuplicates: false`. When any duplicate SKU or barcode existed in the batch, the entire `createMany` operation would fail, causing most products to be skipped.

Additionally, the function was incrementing the `created` counter before actually inserting, which inflated the count even when inserts failed.

### Solution
Changed `promoteAllCatalogProducts()` to use individual inserts instead of batch inserts:

1. Replaced `createMany` with individual `create` calls in a loop
2. Each product is inserted individually; if one fails due to a duplicate, the rest continue
3. Only increment `created` counter after a successful insert
4. Track `errors` separately for failed inserts

**File:** `src/main/catalog/catalogQueries.ts`

```typescript
// Before (batch insert - fails entirely on any duplicate):
await db.product.createMany({ data: buffer, skipDuplicates: false })

// After (individual inserts - graceful duplicate handling):
for (const item of buffer) {
  try {
    await db.product.create({ data: item })
    created++
  } catch {
    errors++
  }
}
```

This ensures all products are attempted, and only true errors (not duplicates) are counted as failures.

## 8. Fixed Barcode Unique Constraint Error During Catalogue Commit

### Problem
When committing a catalogue import, the system crashed with:
```
Unique constraint failed on the fields: (`barcode`)
```

This happened when the reconciliation logic tried to update a product's barcode to a value that was already assigned to a different product in the database. This commonly occurs when:
- Two products swap barcodes between catalogues
- A barcode is reassigned from one product to another
- Multiple products in the batch have conflicting barcode assignments

### Root Cause
**File:** `src/main/catalog/importService.ts`

The `commitImport()` function was applying all product updates in a single transaction. When two products tried to swap barcodes (Product A gets Barcode B, Product B gets Barcode A), the second update would fail with a unique constraint violation because the first product already took the new barcode.

### Solution
Modified the commit phase to handle barcode conflicts gracefully:

1. Split updates into barcode updates and non-barcode updates
2. Apply all non-barcode updates first (no conflict risk)
3. Apply barcode updates one-by-one with try/catch
4. If a barcode update fails due to a unique constraint, clear the barcode instead of aborting

**File:** `src/main/catalog/importService.ts`

```typescript
// Split updates by type
const barcodeUpdates = plan.updates.filter((u) => u.data.barcode !== undefined)
const nonBarcodeUpdates = plan.updates.filter((u) => u.data.barcode === undefined)

// Apply non-barcode updates first
for (const update of nonBarcodeUpdates) {
  await tx.product.update({ where: { id: update.productId }, data: update.data })
}

// Apply barcode updates with conflict handling
for (const update of barcodeUpdates) {
  try {
    await tx.product.update({ where: { id: update.productId }, data: update.data })
  } catch {
    // Barcode conflict — clear the barcode to avoid unique constraint violation
    await tx.product.update({
      where: { id: update.productId },
      data: { ...update.data, barcode: null }
    }).catch(() => {
      // If even clearing fails, just skip it
    })
  }
}
```

This ensures that:
- The commit never fails due to barcode conflicts
- Products with conflicting barcodes are set to `null` rather than blocking the entire import
- All other updates (cost, price, name, etc.) are still applied correctly
- The pharmacist can manually fix barcodes later if needed
